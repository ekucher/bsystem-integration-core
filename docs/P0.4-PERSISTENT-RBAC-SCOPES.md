# P0.4 — Persistent RBAC & Scopes

## Goal

Move authorization policy out of Go source code and into PostgreSQL so BSYSTEM can administer roles, permissions, module access and scoped grants without rebuilding Integration Core.

## Persistent RBAC model

```text
authentik group
      ↓
group_role_mappings
      ↓
roles
      ├── role_permissions → permissions
      └── role_modules     → modules
```

Human and service roles are separated by `roles.kind`:

```text
human
service
```

## Seeded human roles

- Administrator
- Manager
- Developer
- QA
- Support
- DevOps
- Customer

## Seeded service role

- Service Core

The `BSYSTEM-Services` authentik group maps to the `Service Core` role. Service permissions are therefore no longer hardcoded in the HTTP middleware.

## Scopes

`principal_scopes` adds resource-level authorization on top of base role permissions.

Supported scope types in P0.4:

```text
global
tenant
client
project
resource
```

Example:

```text
principal_type = user
principal_id   = USR-000017
scope_type     = project
scope_id       = PR-000103
permission_id  = projects.task.read
```

This means that the principal receives that permission for project `PR-000103` even if the role is shared with users who have different scopes.

## Admin API

Administrator-only endpoints:

```text
GET    /api/v1/admin/rbac/roles
GET    /api/v1/admin/rbac/scopes?principal_type=user&principal_id=USR-000017
POST   /api/v1/admin/rbac/scopes
DELETE /api/v1/admin/rbac/scopes
```

Example scope grant body:

```json
{
  "principal_type": "user",
  "principal_id": "USR-000017",
  "scope_type": "project",
  "scope_id": "PR-000103",
  "permission_id": "projects.task.read"
}
```

Scope grant/revoke operations are written to the audit trail as:

```text
rbac.scope.granted
rbac.scope.revoked
```

## Security rules

- authentik remains the source of identity and group membership;
- PostgreSQL is authoritative for BSYSTEM roles and permissions;
- backend authorization remains authoritative;
- UI visibility is not an authorization control;
- service roles cannot be resolved as human roles and vice versa;
- only Administrator can use the RBAC administration API in P0.4;
- scope checks must be enforced on tenant/client/project/resource endpoints before those endpoints are exposed to Customer roles;
- access tokens and credentials are never stored in RBAC tables.
