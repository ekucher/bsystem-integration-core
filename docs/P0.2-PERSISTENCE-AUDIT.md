# P0.2 — Core Persistence & Audit

## Goal

Turn Integration Core from a stateless RBAC gateway into the persistent platform metadata layer required by BSYSTEM-HUB.

## Scope

### PostgreSQL

P0.2 owns these platform tables:

- `identities`
- `modules`
- `global_id_counters`
- `global_entities`
- `audit_events`

Migrations are embedded into the Go binary and applied during startup. Migrations must remain idempotent until a dedicated migration version table is introduced.

### Identity mapping

On every authenticated request Integration Core synchronizes the authentik identity. The first successful request allocates a stable BSYSTEM user ID:

```text
authentik subject
      ↓
USR-000001
```

Email, display name, username and groups may change without changing the Global User ID.

### Global ID registry

Global IDs are allocated transactionally from PostgreSQL counters.

Examples:

```text
CL-000001
PR-000001
SRV-000001
INC-000001
DOC-000001
```

A source entity mapping is idempotent by:

```text
(source, entity_type, source_id)
```

### Module registry

Module names, descriptions, state and ordering are persistent platform configuration. Frontend visibility still depends on effective RBAC.

### Audit

Security-relevant and administrative operations must generate immutable audit rows. P0.2 records Global ID administration and provides the base storage for later login, configuration, adapter and AI audit events.

### NATS

Integration Core publishes platform events when persistence state changes. NATS is intentionally non-critical for the synchronous HTTP API: temporary broker loss must not prevent authenticated reads from PostgreSQL.

## Security rules

- databases are not publicly exposed;
- Global ID creation/resolution is Administrator-only in P0.2;
- audit listing is Administrator-only;
- tenant-aware authorization must be added before exposing Global ID resolution to Customer roles;
- access tokens are not persisted;
- no passwords or secrets are written to audit metadata;
- `X-Forwarded-For` is trusted only when the production reverse proxy topology is controlled.

## Tests

CI executes:

```text
go mod tidy
gofmt (validation working copy)
go vet ./...
go test ./...
```

The test job starts PostgreSQL 17 and verifies:

- migrations;
- stable user Global IDs;
- client Global ID creation;
- Global ID resolution;
- audit insertion and reading;
- RBAC resolution.
